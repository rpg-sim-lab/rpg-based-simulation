## Request Summary
Reported by lead-planner-u24 / rpg-planner (u24) through lead-planner on 2026-11-20: at main 0c18f6151, 20 pyrefly errors are not in codebase/baselines/pyrefly_baseline.json, and none come from a split's diff. They are tactical_hold.py ×13, search.py, information/resolver.py, information/router.py, observability consumer.py, watchdog.py, groups.py, and intelligence.py:390 col 59 (the `staged` argument of `reinferred_blockers_update`). The likely cause, still unverified, is #975 moving pyrefly to 1.4.1. Pyrefly is report-only (test.yml runs it with continue-on-error; TCK-20261021-PYREFLY-ADVISORY-REPORT), so nothing is red. The advisory report is noise until the drift is cleared.

## Scope
1. On one pinned main SHA, run pyrefly at the old pin (1.3.x, from TCK-20261021) and at 1.4.1. Record which of the 20 appear only under 1.4.1, which are real code drift, and the wall time and peak memory.
2. For each group: re-baseline (the error is a new pyrefly rule or inference change on unchanged code), stating which pyrefly change it is; or fix it, when the error is real. A fix in src/ goes to rpg-planner as a finding, not as a codebase edit.
3. Regenerate the baseline with the project's pyrefly baseline command. Never hand-edit it.

## Out of Scope
- Making pyrefly blocking.
- mypy baseline changes.
- Re-keys from splits (those go with their split; see TCK-20261120-CODE-HEALTH-MOVE-CARRIES-RENAMED-SYMBOLS-AND-PARTIAL-ROW-SETS).

## Acceptance Criteria
