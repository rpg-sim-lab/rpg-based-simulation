## My recommendation to rpg-designer: (a) keep the hook outside the gate at 30
- **Case:** the packet calls itself PRE-BIND, a world_dynamics sub-phase outside its cadence gate, and I agree. `refine()` gains no phase. kernel.md's 7-phase loop is untouched, so this is not a STOP.
- **Why not inside the gate:** the cadence there is 50, so births would run every 50 ticks (40% fewer checks) or every 150 (80% fewer). D1's per-check chances were sized for a 30-tick check, so either option means re-ruling D1's values. Outside the gate, no ruled value changes.
- **Order:** on a tick where both fire, world_dynamics runs first and births second, through the same generator, so the newborn ids follow. A named test pins this.
- **It replaces an existing step:** the old humanoid reproduction step (inside the gate, every 50 ticks) is removed, so this is one births step, not two.
- **My four conditions (c32eb73f):**
  1. Absolute-tick cadence key: met (`state.tick % 30`).
  2. Typed updates through the apply path in a fixed, tested order: met.
  3. Docs regenerated if the phase list changes: met, because the list doesn't change. phase_inventory is regenerated by its generator only if there is a real diff.

## Two corrections before rpg-designer rules on the docs text (the second is settled in v3)
1. **The optional "Births Law" bullet contradicts the packet's own §2.** It says "it reads only the two parents and the species' reproduction profile". §2 lists more reads: regions, the spatial index, home/leash position, home_region_id and public_reputation. It also leaves "fed" undefined. My proposed replacement, which is rpg-designer's to accept, edit or drop (anchor: after the `- **Sovereignty Law**:` bullet in docs/engine/authoritative_pipeline.md, which occurs once):
   > `- **Births Law**: Every 30 ticks (absolute kernel tick), a mother eligible under her species' reproduction profile, with an eligible same-species mate in range, may bear one newborn at life stage CHILD, by the profile's chance per check, drawn from the run's seeded RNG. The step runs inside this phase, outside its 50-tick gate, and commits only typed updates (the newborn, its birth source, the parents' cooldowns and the mother's hunger cost, the region's birth count).`
2. **Unruled reads: SETTLED in v3.** None of these reads decides eligibility or the mate; mate range is `mate_radius_tiles` around the mother, per Q3. Each one is a value written to the newborn. This is rpg-planner-ubuntu's code read at b423a6541. The implementer's own answer may follow, and anything it changes comes back to me.
   - **home_region_id:** the mother's, else the birth region (code-level ruling 3).
   - **public_reputation, Q18a, ruling (a):** keep it. `build_newborn` passes both parents' reputations to the existing `V2EntityBuilder.birth_record` (src/core/builder.py:661-702, idea 53). That seeds the child's value from `ReputationService.combine_public_reputation` of the two. I confirmed this on main. It is an existing builder law, so births follow it rather than opening a second birth law. It is not a good: D3's "nothing from nothing" covers goods and gold, not standing. Disclose: "public_reputation = the parents' combined value (existing birth_record law, idea 53)".
   - **home_position and leash_radius, Q18b, ruling (a):** keep them. The newborn takes the mother's home anchor and leash range, for the same reason as G1a: it belongs where its mother belongs. Omit each field when the mother's is None, and disclose it.
   - The Births Law replacement text in correction 1 already covers this: it names no reads beyond the mother's eligibility and the mate in range.
