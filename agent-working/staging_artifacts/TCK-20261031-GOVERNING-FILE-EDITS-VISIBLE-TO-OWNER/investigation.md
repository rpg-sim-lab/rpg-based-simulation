## Q1. Does the guard's PreToolUse hook see Edit and Write as well as Bash?
Yes, under the current matcher. `.claude/settings.json` wires the guard to `Bash|Edit|Write|MultiEdit|NotebookEdit|SendMessage` (read from the file, not assumed). `guard.py` already classifies edit tools via `cl.classify` -> `classify_path`. Not a settings question. Two things the matcher does not cover, both inside the guard script, not settings:
- `main()` has a Bash fast path (`_AUTHORITY_TEXT`) that returns 0 before classifying. It names `CLAUDE.md`, `settings`, `hooks/` but not `guard.py`, `classify.py` or `.github/workflows`. New paths need adding there or a Bash edit of them is never seen.
- `_guard()` returns early when `classification.is_authority` is false, and `decide()` returns "allow" for an unresolved caller. The event must be written before that early return, and must not depend on a resolved role (seat falls back to `unresolved`).

## Q2. Widen GOVERNING_FILE_EDIT or add a second list?
Pinned today: `tests/tools/test_session_classify.py` lines 32-33, 83-87, 227-230 (positive rows for CLAUDE.md, settings, hooks dirs); `tests/tools/test_session_guard.py::test_governing_and_authority_file_edits_are_allowed_for_every_role` (allow for every role). `test_session_boundary.py` line 54 uses `tools/sessions/guard.py` as an edit path in a boundary-advisory case. I found no test asserting that guard.py, classify.py or .github/workflows classify to NONE, but the boundary test edits guard.py and expects only the role_boundary advisory.

Option A, widen `GOVERNING_FILES` (and so the action): `classify_command` flags any non-read-only segment that merely *mentions* a path (`mentions_governed`, substring match). `python3 tools/sessions/guard.py`, `git add .github/workflows/x.yml`, `gh workflow run` style text would all become governing_file_edit. Noise in the very count the retro uses; also changes what `classify` returns for guard/classifier edits, which the boundary advisory path currently relies on being NONE-class.
Option B, a second list (recommended): one definition `GOVERNING_PATHS` in `classify.py` = existing `GOVERNING_FILES` + `GOVERNING_DIR_MARKERS` + guard.py + classify.py + `.github/workflows/`, with a pure `governing_paths_in(path_or_text)`; `GOVERNING_FILE_EDIT` and its tests unchanged. `Classification` gains `governing_paths: tuple[str, ...] = ()`, filled for edit tools by path and for Bash by the same read-only test as today. `is_authority` is unchanged, so no new allow/ask behaviour. Reusable by plan 28a's gate job (pure function, stdlib, no guard imports) and by pr_render. Breaks nothing pinned. CORRECTION (planner review 1): B protects the *action* and the classify results, not the *count*: filling `governing_paths` from a non-read-only Bash mention still writes rows for `python3 tools/sessions/guard.py` or `git add .github/workflows/x.yml`. Handled by a row field `basis`, not by pretending it away. The cost is two lists that must not drift, handled by a test that asserts `GOVERNING_FILES` is a subset of `GOVERNING_PATHS`.

## Q5. Where the event is written
In `guard._guard`, immediately after `classify`, before the `is_authority` return: `_record_governing(payload, classification)` in a bare try/except, so a failure never changes the exit code or output. Row to a new family `governing_edits.jsonl` in `agent-working/agent-monitoring/data/<iso-week>/`, through the same shared locked writer `boundary.write_event` uses (generalise it with a `family` argument, default `role_boundary.jsonl`; no behaviour change). Fields: `ts`, `event: "governing_edit_attempt"`, `seat`, `path`, `attempt: true`. No tool name, command text, session id or content. Seat: reuse `resolve_caller` (cost only paid on a governing edit) with fallback `unresolved`. The row is written at PreToolUse, so it is an attempt: the call may later be denied or fail, or the edit reverted. One row per path per call.
Speed: non-governing calls pay one string/path check (no I/O). Bash with no governing path pays nothing extra.
Bash path extraction: today Bash detail says only "a governing file". The new code extracts the matching path tokens from the non-read-only segment.

## Q6. Retro line
Report: `tools/agent-monitoring/session_layer_report.py` (it already renders `role_boundary` warnings, with `load_family`). Add `### Governing-file edit attempts` with: attempts per path, and for the same period the merged commits on origin/main touching each governing path, computed with the same `governing_paths_in` over `git log --name-only`. Matching is by path and period, not per event: we cannot match an event to a PR body list, and the PR body is not a source of record. "Unmatched" = a path with attempts and no merged commit touching it in the period. Honest reading: unmatched covers a reverted edit, a denied or failed attempt, work not yet merged, and a real edit that never went through review; the line is a prompt to look, never a violation count. Also reports total attempts vs total governing-touching merged commits. Dark-family note when the file family has no rows (same `_dark` convention).

## Amendments from planner review (7 changes, all accepted)
1. Row field `basis`: `path` (edit tools, exact path match) or `mention` (Bash, text match, may not be an edit). The retro shows the two separately. Docs say mention rows over-count.
2. The new list does NOT use the `/hooks/` marker (it matches `frontend/src/hooks`, React code). It uses repo-relative prefixes `.claude/hooks/`, `tools/hooks/`, `codebase/hooks/`; `frontend/src/hooks/...` is a negative test. The existing marker and `GOVERNING_FILE_EDIT` stay as they are. Docs: hook scripts wired from other directories are not on the list.
3. Rows hold repo-relative paths only, computed the way `boundary.py` derives `rel`; a linked worktree's absolute path must resolve to the same relative path. A path outside the repo (e.g. a user-level settings file) writes no row, because it can never appear in a PR; stated in the docs. Both tested.
4. Tests never write live shards: the data dir is redirected for the whole of `tests/tools/test_session_guard.py` (autouse fixture), one test asserts the real week dir is untouched, and other `tests/tools` callers of the guard are checked and covered.
5. Fast path: adding names to `_AUTHORITY_TEXT` sends those Bash commands on to `classify` and `_advise`. To be checked at implementation: an uncertain classification is only produced by indirection/unparseable text plus authority words, and `decide` asks only for critical actions or `uncertain_critical`; a plain mention of guard.py should yield `Classification(frozenset())`, then `_advise` (which only handles EDIT_TOOLS and SendMessage, so a Bash call returns nothing). Test: Bash mention of guard.py with no other authority action gives identical output (empty) to today. If it cannot stay identical, stop and tell the planner.
6. API split: `governing_path(path, repo_root=None)` exact, repo-relative matching (edit tools, pr_render, retro, 28a); `governing_mentions(command_text)` separate, returning only matched tokens, never the rest of the command.
7. Docs also: `docs/agent-monitoring/schema.md` documents the new family (role_boundary is there); check `validate.py`, `week_close.py` and anything else listing families. Retro text: an attempt in one week can merge the next, and rows reach main only when a branch carries them, so "unmatched" can mean either.
Retro basis note for the ticket: the retro compares attempts with merged commits by path and period, replacing "against the PR lists" in the ticket, because PR bodies are not a source of record and an event cannot be tied to one PR body.
