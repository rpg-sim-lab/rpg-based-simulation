## 1. Where an escalated need loses (static)
`StrategicIntelligenceSystem.evaluate_strategic_intent` (src/systems/strategic_systems/intelligence.py): `ScoreModifierSystem.apply_modifiers` (:1373) -> the winner is the first score with utility >= 20 and a target (:1378) -> `route_live_record` (:1396; a matching record that is already current is a no-op = a win) -> the generic candidate (:1527-1550, `lock_until_tick=min(t+10,t+50)`, score = utility) -> `orphan_switch_candidate` (:1552) -> the capacity gate (:1554) which already lets an escalated need through (`escalated_need_wins`, the ONLY use of that function) -> `evaluate_project_switch(with_live_current_score(...), candidate, t, state)` (:1559) -> `supersede_on_win` -> if the switch is truthy the update returns (:1562-1585), else an empty update (:1587/:1610). `evaluate_project_switch` (:777-873): no current id, or the current not ACTIVE, creates the candidate unconditionally (:809-822); otherwise the retention margin `interruption_resistance x resistance_multiplier` (<= 13.5 at need > 70; :825-827) and the LOCK block (:829): a current with `lock_until_tick > t` is released early only by `_threat_resolved` (:839), `detour` passes unconditionally (:848), every other kind needs `candidate_pct > normalized_effective_current_pct and candidate_pct > _INTERRUPTION_URGENCY_FLOOR_PCT (0.8)` (:851-861), so a candidate with utility <= 80 can never beat a LOCKED current; the base comparison (:863) `candidate.score > current.score + retention_margin` otherwise (:873 returns None = the loss). A freshly switched-in current carries a 10-tick lock (:1550). Nothing in the switch, in live_record_route.py or in `_threat_resolved` knows about an escalated need; `detour` is the only unconditional bypass.
What the data says about WHICH gate (group A, utility <= 80, town_return current): consistent with the lock's 0.8 floor, but whether each town_return was inside its 10-tick lock is not in the rows (UNCONFIRMED). Group B (utility > 80, resolve_blocker): the lock's normalized comparison or the base retention comparison; not decidable from the rows.

## 3. The smallest place and what data it reads
One place: `evaluate_project_switch`, before the lock block (before :829). No settings exist for the switch (lock floor 0.8 is a code constant at :53, the margin comes from the code-derived profile, cognition_capacity.py:34); the rule needs none: the escalation onset is the tree's own `need_is_pressing` (need_pull.py) and the threat test is `present_threat_to` (present_threat.py). The switch must do what an ordinary win does: SUSPEND the current (`suspend_record`, suspended_since = tick, :865) and set the candidate current, the same update.

## 4. Fatigue only on the K2 head (answer to "why fatigue appears only on the K2 head")
The before-fix K3 had fatigue 0 and hunger 26; the K2 head has fatigue 2 and hunger 28. After (A), a broke subject's fatigue project ends with the typed WAY_CLOSED (`end_record` clears the current project and objective, no cooldown, lock or blocker is written, per the audit); on the re-decide the current is empty and a winning fatigue candidate is created unconditionally (:809), so (A) itself cannot cause a fatigue switch loss. Both fatigue losses here (group C) have a HUNGER project current, i.e. a need-against-need case that exists only if both needs are pressing, which the K2 fix made reachable because the fatigue project is no longer parked at the inn.
