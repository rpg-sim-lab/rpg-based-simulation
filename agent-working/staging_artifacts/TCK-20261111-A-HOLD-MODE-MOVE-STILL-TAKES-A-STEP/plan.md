Recommended by rpg-designer 2026-11-14; the owner request goes through lead-planner-u24 (drafts/rpg-designer-hold-mode-owner-row.md). Cites: #715 6843780354 (run the ticket), investigation.md sections 1-10. One change in three pieces, built together.

## What each piece is, with the files
- **P1 (the entry tick).** The walk check also honours what THIS tick's pending update decided. File: src/engine/candidate_selector.py (`holds_action_task`, :227-234, and `movement_target`, :152-179, the `elif holds_action_task(entity)` at :172). Caller `resolve_live_tracking_target` (:91) keeps the entity-only form.
  - **A flaw in P1 as specified, found while drafting (needs the designer's word before the build):** the plan text is "also counts an action task set by THIS tick's pending update (ENTITY_ACT with a payload, the same test)". By the time `movement_routing` runs (pipeline.py:301) the actions phase has already run (pipeline.py:299) and, for a successful HOLD, replaced the update's task payload with `{}` (pipeline_phases/actions.py:317-328). So at movement time the typed wait's pending task is ENTITY_ACT with an EMPTY payload, the "with a payload" test is False for exactly the typed waits, and P1 as worded would not stop the entry-tick step. Two ways to make P1 work, designer to choose: **P1-a:** count a pending ENTITY_ACT regardless of payload (broader: it would also suppress the same-tick stored-target step of any action that completes this tick, e.g. EAT, REST); **P1-b (narrower, recommended for the draft):** `movement_target` returns None when the pending update carries `navigation.target_clear` and no `target_set` (the update itself clears the target, so there is nothing stored to walk). P1-b needs P2 for the typed waits and already covers ATTACK/SKILL emissions (they carry `target_clear=True`: tactical_hold.py:49, tactical.py:740) and the kill and collapse holds (actions._hold_in_place, sleep_debt.collapse_update both set `target_clear=True`). The unit tests below are written to P1-b and to the as-specified P1 where it fires (ATTACK/SKILL with a persisting payload).
- **P2 (the gap).** The typed waits clear the stored target in the same update that sets HOLD. Files: src/engine/tactical_hold.py (`notice_unengaged_hostile`: the WATCH_HOSTILE update :105-109 and the AVOID_NO_ROUTE update :114-118 add `target_clear=True` to their `NavigationUpdate`) and src/engine/tactical.py (the HOLD_CHOKEPOINT update :620-626). The next decision writes a new target if it wants one (measured: it never re-chose the same target, 0 of 17). Known limit (investigation 9, C2): the objective path (intelligence.py:666-670, redirection.py:123-128) re-derives its target at the next strategic pass (cadence 10), mode-less; P3 is what keeps that walk off HOLD pricing.
- **P3 (the lifecycle).** HOLD resets to the navigation default (`NavigationComponent.movement_mode` = WANDER, state.py:494) when its entering task ends, for all five writers, as a typed `movement_mode_set=MovementMode.WANDER` in the SAME update that ends the task. Files: src/engine/pipeline_phases/actions.py (the task-end branch at :317-328, which already ends the task for HOLD success, survival-action ends including a sleep that is rested enough, and unrecoverable failures such as TARGET_INCAPACITATED after a kill). Per writer: WATCH_HOSTILE / AVOID_NO_ROUTE / HOLD_CHOKEPOINT end at their HOLD success (the entry tick); after-kill HOLD ends when the next swing at the dead target fails (actions.py:89-107, one tick later); collapse ends at wake (`_survival_action_ends`, actions.py:51-58). `_hold_in_place` and `collapse_update` need no change.
  - **Open point for the designer (P3 for the typed waits):** the HOLD action succeeds in the same tick the decision sets HOLD, so a reset "in the update that ends the task" resets the mode in that very tick and HOLD is never observable for the typed waits; the hold is then carried by P2's `target_clear` alone. That also drops what the HOLD mode does for others (an occupant in HOLD is not made to yield, movement.py:116; a HOLD party refuses a swap, pipeline_phases/movement.py:327-329; HOLD counts as resting for stamina, apply.py:175) for the wait. If those are wanted for the duration of a wait, an alternative for the typed waits is to end HOLD at the NEXT DECISION (the existing behaviour) and reset in the mode-less target writers instead (intelligence.py:649, :670; redirection.py:97, :128; tactical_hold.py:99 KEEP_WALKING, which inherits the current mode). The build waits for this answer.
  - `tactical_hold.py:99` (KEEP_WALKING) must not inherit HOLD: pass WANDER when the current mode is HOLD (part of P3).
