## Q1. Why the refusal never reaches infer_blockers
`infer_blockers` is a thin delegate (intelligence.py:175-183) over blocker_lifecycle.py:64-157, called once at intelligence.py:375-380 with the task's work_kind and payload, `navigation.last_failure_reason` and the current project. It reads: (1) a nav failure string "PATH_NOT_FOUND"/"STUCK"/"OSCILLATING" plus payload target_position (:82-92); (2) wait_count >= 5 or oscillation_count >= 3 (the congestion blocker, :95-101); (3) INTERACT capacity failures on harvesting (:104-122); (4) rejected intent results INSUFFICIENT_CAPACITY / INVENTORY_FULL / OUT_OF_STOCK / "LIQUIDITY_EXHAUSTED" (:125-147). Two of those branches look dead against the typed enum values (ReasonCode.PATH_NOT_FOUND == "path_not_found", LIQUIDITY_EXHAUSTED == "liquidity_exhausted", enums.py:102,167, lowercase against uppercase strings; and no writer of "STUCK"/"OSCILLATING" was found), reported as a finding, not touched here. It does NOT read project_giveups, the navigation experience memory, payload outcome/reason, or any (action, building) counter.
Cause, per action (both layers):
- EAT: RECORDED, NOT MAPPED. The refusal is `navigation.last_failure_reason` (SOURCE_MISSING, or INSUFFICIENT_GOLD via `refusal_reason`, action_router.py:22-37), but infer_blockers has no branch for it and the task payload (the only holder of the building id) is wiped to {} when the reason ends the task (actions.py:52-56, :334-341).
- REST (the v6 case), SELL, REPAIR: NOT RECORDED at all. [read] building_services.py:75-95: `service_delta` returns None when `admits_at` is false, `with_service` returns the bare updates, so no refusal, no transfer, no failure_reason; economy.py:80 skips an entity with no resource_transfers, so no IntentResult for b exists ("absent"). The only typed REST refusal is NO_BED_FREE (lodging.py:123-129, via `no_bed_in_reach`), which is a bed refusal, not a payment one.
So the ticket's Q1 answer: the failure is not recorded for REST/SELL/REPAIR and not mapped for EAT; the building id is not carried by any typed refusal.

## Blocker mechanics a new blocker would meet (agent 1, file:line)
- Suppression: ScoreModifierSystem.apply_modifiers step 5 (score_modifiers.py:53-60): an `access` blocker whose subject equals the score's target_id multiplies utility by 0.1; a hunger or fatigue score is floored at 0.2 x its raw utility (:63-64), so it is SOFT. The hunger target_id is `str(building.id)` (scorers.py:136-141), so subject "20003" would match. `ways_in_reach` (ways.py:47-62) reads no blocker.
- Lifecycle: a blocker is refreshed by re-inference (`merge_inferred_blocker`, strategic.py:353-358, keeps failure_count and suppression, refreshes last_seen_tick). A resolve_blocker project older than 50 ticks ends BLOCKER_TIMEOUT and sets failure_count + 1 and suppression_until_tick = now + 100 x 2^(n-1), capped at 800 (strategic.py:340-350, intelligence.py:1257-1270). BLOCKER_TIMEOUT ends the PROJECT, it does not remove the blocker. The only removal is `quiet_blockers` (strategic.py:361-369), which removes ONLY the congestion blocker after BLOCKER_QUIET_SPELL_TICKS = 200 of quiet. An access blocker with a non-coordinate subject is never passively resolved (blocker_lifecycle.py:238-249). Precedent exists: the congestion blocker (subject "congestion") already runs this lifecycle.
- Data path: data/content/strategy/blocker_settings.yaml (`access_giveup_limit: 4`), schema `BlockerSettingsDefinition` (content/schema.py:418-421), reader src/content/blocker_settings.py (`access_giveup_limit()`, no code default); a new threshold is a new field on that one record plus a getter, and it enters the catalog fingerprint.
- Per-subject state: no existing counter fits (wait_count and oscillation_count are movement counters, project_giveups is per anchor and purpose, last_failure_reason is one latest value with no count and no building id). A new typed counter is needed; natural home NavigationComponent next to giveup_records (navigation_component.py:48-49), with a NavigationUpdate field, a patch rule (patches.py:329-335), a copy in apply._fast_replace_navigation (apply.py:738-754) and probably a FIELD_RULES row (comment at navigation_component.py:45), omitted from the canonical dict while default (navigation_component.py:84-91), so the hash is unchanged until a subject accrues one. A filed blocker does change the replay fingerprint (`_blocker_ident`, replay/fingerprint.py:22-31).
- Existing give-up mechanism (not a blocker, #996): `destination_suppressed` (strategy/destination_suppression.py:95-117) refuses a target within Chebyshev 1 of a pending give-up record or an active navigation experience of the same purpose; `project_giveups` counts toward `access_giveup_limit` (blocker_lifecycle.py:348-362), whose comment says it "Files NO ACCESS blocker". This is the nearest existing "N failures of one way, then refuse that way until due" machinery; see Open question 4.
