# Investigation: the six social action kinds and the perception slice

Code read only (nothing run). Base: origin/main 4dc2c82cb. Dispatch: rpg-planner brief of 2026-11-13; owner approval #715 6843004519 (and 6843079519). Line numbers are from that base. RECRUIT is the precedent (#883, divergence 2.205).

## 1. The router and the one general door
- Router: src/engine/domain/action_router.py:63-84 dispatches RECRUIT, TEAM_UP (:66), TRADE (:69), TRAIN (:75), PROPOSE_MARRIAGE (:78), JOIN_CLAN (:81), LEAVE_CLAN (:84) after the readiness check (:58).
- The router is reached from two places only: `SimulationDomainLogic` (src/engine/domain_logic.py:54), which routes the payload of an ENTITY_ACT task, and `ActionIntentAdapter` (src/engine/intent/action_intent.py:305).
- The adapter has a general door: its `else` branch (:302-303) sets `router_payload["action"] = intent.kind` for any intent kind it has no branch for. So any ActionIntent whose `kind` is "TEAM_UP" etc. would reach the router. Every ActionIntent constructed in src has one of: ATTACK_TARGET, MOVE_TO (combat_engagement/resolver.py:41-65; information/resolver.py:52), ASK_INFORMATION (information/resolver.py:78), HARVEST_RESOURCE (tactical_objective.py:79), or the adventure resolver's kind set (adventure/resolver.py:86: ACCEPT_QUEST, ATTACK_TARGET, MOVE_TO, HARVEST_RESOURCE, ASK_INFORMATION, RETURN_TOWN, CHANGE_OCCUPATION). None is a social kind.
- Every other site in src that builds an ENTITY_ACT payload with an "action" key emits one of ATTACK, SKILL, HOLD, EAT, SLEEP, REST, INTERACT, SELL, WORK (tactical.py:625,726,744; tactical_hold.py:40,108,117; tactical_flight_guard.py:76; tactical_avoid.py:80; tactical_objective.py:67; tactical_rest.py:85,106,138; sleep_debt.py:72), plus building_arrival.py:40 (`_act`), which emits only SELL, EAT, WORK, REST (:56-75). No emitter of any social kind.
- Searched every spelling (quoted, unquoted, lower case): TEAM_UP, TRADE, TRAIN, PROPOSE_MARRIAGE, JOIN_CLAN, LEAVE_CLAN occur in src only as: the router; the execute_* bodies; ContractKind (core/strategic.py:101); enums TEAM_UP_ACCEPTED/DECLINED (core/enums.py:190-191); the "TRADE" label in `src/town/buildings.py:20` services list (read by no emitter: the live service table is SERVICE_KINDS, building_services.py:29, which has REST, EAT, SELL, REPAIR); and the JOIN/LEAVE_CLAN outcome reader (pipeline_phases/clan_lifecycle.py:55,61). The only callers that pass these action strings are tests: tests/unit/social/test_marriage.py:168, test_teach.py:145, test_clan_appraisal.py:118, tests/unit/resource/test_resource_v2_boundary.py:298, tests/unit/kernel/test_executor_context_parity.py:89.

## 3. Clans: no clan exists in play to join or leave
`state.clans` starts as an empty dict (core/state.py:1428). The only writers are `ClanUpdate`s applied at engine/apply.py:478-490, which creates a ClanState if absent (:483). The ClanUpdate producers are: ClanLifecyclePhase (join/leave of a named clan_id, succession, dissolution), groups.py:150-237 (a reputation delta for the clan of a defecting member, found with find_clan_id_for_entity), and contracts.py:294 (a reputation delta). Each acts on a clan_id that must already exist, except a join, which first requires `context.clans.get(clan_id)` (core_actions.py:551-557). I found no site that creates a first clan from a world or at run time (grep ClanState( outside core/engine/apply: none; generator.py's "orc_clan" is a faction label, line 30). So JOIN_CLAN could not succeed even if something issued it (TARGET_NOT_FOUND), and LEAVE_CLAN returns NOT_A_MEMBER. (This is the read; a spy would confirm `len(state.clans)` stays 0.)

## 5. Scope 4a: why perception can fail at distance 1 for an adjacent, catalog-hostile neighbour
Two different "hostile" tests are in play.
- Catalog-engagement test: `LegalityServiceV2._is_engagement_hostile` (legality.py:537-550) = `are_entities_hostile(entity, other, RelationContext(distance=1.0, combat_engaged=True))`. It is what `get_engaged_hostiles_at_pos` uses (:553-594).
- Perceived-hostile test: `hostility.perceived_hostile` (hostility.py:94-97) = `relation(...) in ATTACK_RELATIONS` (FACTION_HOSTILE, PREDATION). It differs from the first in four ways, any of which makes an adjacent catalog-hostile neighbour not perceived-hostile:
 1. `perceives()` first (appraisal.py:44-54, called at hostility.py:60): False if `other` is dead, or if either is `lodged_in` (:48-49, divergence 2.155), or if the perception gate says no. (Gate math, gate.py:133-161: score = sense x signal x distance_factor x terrain x (0.5+alertness x 0.5); the caller passes only distance, so terrain 1.0 and alertness 0.5 give x0.75; distance_factor at 1 is 0.98; threshold 0.2. With the default signals of `get_entity_signals` (behavior_consumers.py:86-104: visibility "medium", noise/scent/life/vibration "low") and every profile in data/content/living/sense_profiles.yaml, vision medium x visibility medium gives 0.36 x 0.735 = 0.2646, which passes. No content file sets a visibility/noise/scent signal property (grep: only gate.py and behavior_consumers.py read them). So on today's content the gate does not fail at distance 1. It would fail a source whose best sense x signal product is below 0.272.)
 2. Wild creature on either side: `faction_hostile` returns False (hostility.py:62-63, decision 47); the pair is then judged by `appraise`, and only PREDATION counts (THREATENING, WARY and NONE are "avoided, never engaged", hostility.py:94-96).
 3. The relation context: `faction_hostile` passes `combat_engaged=is_engaged(entity, other)` (:66-71), true only when one names the other as its target, and leaves `intruding` unset; `_is_engagement_hostile` always passes `combat_engaged=True`. The catalog label "intruder" is hostile only when `intruding or combat_engaged` (content_semantics/faction.py:227-230); "threat" needs `combat_engaged` or distance <= 5 (:223-226). A pair labelled intruder, not yet engaged and not flagged intruding, is catalog-engagement-hostile and not perceived-hostile.
 4. Same species (hostility.py:86-87) returns NONE before appraisal.
 Separately, the goal-scorer list `perceived_hostiles` (ai/goals/scorers_support.py:16-26) is a third test: neighbours within ENTITY_TARGET_PERCEPTION_RADIUS, cut to 5 by `SensoryFilter.filter_saliency`, with `combat_engaged=True` and no gate: an adjacent hostile can be dropped by the saliency cap.
 The read cannot say which of 1-4 produced the 149 rows in frontier_marches s42; that needs a measurement (which clause returned False per row). Candidate 3 (intruder label with combat_engaged False) and candidate 2 (wild pair appraised WARY/THREATENING) need no unusual state; candidate 1 needs a lodged entity or a changed signal; the gate needs a source with weak senses.

## 6. Scope 4b: why a RETREAT `resolve_move` can return a null result with no failure_reason
src/engine/movement.py:215-331 returns a result with no `failure_reason` in these cases:
 - :230-231 the subject is not `lifecycle.active`: an empty EntityUpdate.
 - :240-241 `current_tick < step_ready_tick` (terrain cost is time, D75): an empty EntityUpdate; a multi-tick wait on a costly tile gives consecutive null results, which fits a run of several ticks (t1953-1959).
 - :270-271 arrived beside an unenterable target: `target_clear=True`, no reason.
 - :305-310 the oscillation replan: `effective_target == last_position` with `oscillation_count >= 3` sets `success=False`, `replan=True`, `effective_target=None`; `reason_code` is still None here, so the result at :404-416 carries `failure_reason=None` with `clear_target`/`clear_path`. A retreat that steps back to the tile it came from three times is this shape.
 Blocked steps carry a reason (:325-331, from verify_movement_legality), and the held flight step carries FELT_LETHAL_FREE_SWING (:181). The read leaves open which of :240, :305 or :230 produced the t1953-1959 rows; the designer's trace rows would separate them (an empty update vs a clear_target update).

## 7. The designer's town-regroup finding
Two writers send an item-carrier to town: the fast path (systems/strategic_systems/intelligence.py:394-408) and the slow path (:672-680). Both fire when the subject has no objective that carries a position or entity target, `len(pending_inventory.items) > 0`, it is not at (0, 0), a town tile exists and its current target differs; they set `target_set=nearest town tile` with `MovementMode.REGROUP` and `interaction reset`. Nothing in this code discharges the inventory on arrival: the only arrival action that sells is `building_arrival._hunger_arrival` (building_arrival.py:56-57), which runs only for a hunger project whose objective is a shop. A non-hungry carrier that reaches the town tile has its target cleared on arrival, so the next pass finds `target != town_target` and sets it again. What ends it in code: the inventory becoming empty by some other means (a hunger project's sale, a craft that consumes the items, death), or a goal that carries a position/entity objective. Whether carrying items is a reason to go to town at all is a design question: no scorer or intent in src expresses "sell what I carry" for a non-hungry subject (SELL is emitted only from the hunger arrival), so the regroup writer is the only thing that moves carriers, and nothing completes the errand. This is a read, not a measured rate; the 'forever' claim is the designer's measurement.
